# Web planner：初回利用・アクセシビリティ点検と利用者テスト手順

日付：2026-09-19。対象：静的Web版の「設定→比較→保存」。

**実装点検は実施済み、初心者による利用者テストは未実施。** 下記の課題・判定基準を準備した段階であり、参加者の結果や理解度を推定したものではない。

## 実装点検で見つかった問題と対応

| 問題 | 対応 | 確認したこと |
| --- | --- | --- |
| 概要画面から例を再度開くと、編集した人数が例示値に戻る | 初回開始後は「Resume your comparison」を主ボタンとし、例を読み直す操作を「Restart with example inputs」と明示。リセット対象と保持セットへの影響を併記 | Chromeで150人が120人に戻る旧挙動を再現。修正後は125人・条件当たり17語・25%増加・保持セットを保って比較へ復帰。保存段階への復帰も確認 |
| スライダーの数値だけでは単位と丸め後の人数が伝わらない | ラベルを固定し、`aria-valuetext`に増加率と実際の人数・総単語数を設定 | 25%の選択で「157 learners or 44 total words」を確認。ホバーしても読み上げ向けの選択値は変わらない |
| エラー通知と当該入力欄の関連付けがない | 最初の不正入力の`aria-describedby`へエラー説明を追加。既存の入力ガイドは保持 | 空欄時にガイド＋エラーが関連付けられ、修正後にはガイドだけに戻る。入力中のフォーカスも維持 |
| ガイド画面で見出しがH1からH4へ飛ぶ | ガイド中は手順見出しのアクセシブルなレベルを2、結果説明を3、保持セットを4に変更。研究ツール表示では元の階層へ戻す | Chromeで設定・保存の見出しレベル2を確認。自動テストでモード切替と保持セットの階層を確認 |
| フォーカス枠が薄く、スクロール領域等の指定も不十分 | 不透明な濃い青の枠に統一し、`tabindex`を持つ見出し・領域も対象に追加 | Chromeのキーボード操作と画面でフォーカス位置を確認 |

再開は現在の構造を保持するため、対象外の設計を例の構造へ戻して計算制限を解除することはない。例を読み直す操作では、設計・人数・仮定・増加率を例示値へ戻す。保持した仮定セットは残り、新しい共通人数で再計算される。ページ再読み込みでは入力・保持セットとも消える。

スライダーの意味を伝える属性とエラー通知の関連付けは、[W3Cのスライダーパターン](https://www.w3.org/WAI/ARIA/apg/patterns/slider/)および[フォーム通知の説明](https://www.w3.org/WAI/tutorials/forms/notifications/)を参照した。部分的な改善をもってWCAG全体への適合とは判断しない。

- `npm --prefix apps/design_planner_web run check`：最終のコード変更後に成功。再開時の人数・仮定・増加率・保持セット・Rコードの保持、設計ブロックの維持、見出し階層、選択値の読み上げ向け説明、エラー説明の追加・解除を含む。
- `node apps/design_planner_web/stress.mjs`：再開操作を混合操作に組み込み、2,000ステップ成功。数値15,000条件、R一致104条件、極端な値のR出力3例も成功。今回の実行は5.11秒、初期・最大DOM要素数は694。詳細な範囲と限界は[前回のストレステスト記録](web_planner_stress_20260919.md)を参照。
- Chrome：Tab／Enterでスキップリンク→開始→人数・単語数入力→比較へ移動。スライダーをHome／矢印で操作。概要から比較・保存への再開、仮定入力の空欄エラーと回復、保存画面のダウンロードボタンへのTab到達を確認。今回、実ファイルのダウンロードは繰り返していない。
- 通常幅と320px幅で再開・例の再読込の表示を確認。320pxの概要画面・保存画面はページ幅320pxに収まり、ページ全体の横はみ出しはなかった。終了時は通常の表示幅に戻した。確認用タブで取得したerror/warnログは0件。

Chromeのアクセシビリティ情報とDOM属性を確認したが、VoiceOver／NVDA等の実際の音声出力は確認していない。タッチ支援技術、全ブラウザ、全画面のコントラスト、200%以上のズームも今回の網羅検証には含まれない。新しい統計機能・計算式・検証済みパラメータ範囲は追加していない。公開デプロイは行っていない。

## 利用者テストの目的と準備

問いは「初めて使う人が比較を完了できるか」「仮定を変える意味が分かるか」「出力を検出力や推奨人数と誤解しないか」の3つ。操作の成功と解釈の正しさを別々に記録する。

初回は、このツールを使ったことがない想定利用者3〜5名程度で問題を発見する。人数は探索的な作業規模の目安であり、利用者全体の成功率や問題検出率を推定する設計ではない。研究計画に関心があり、人数・単語数・二条件比較を理解できる人を想定する。混合モデルやRの経験は必須としない。R経験と英語画面の読解に困難があったかを記録し、統計概念・画面操作・言語のどこでつまずいたかを区別する。

1人20〜30分を目安に、毎回新しいページから開始する。参加者には課題文だけを渡し、下記の期待結果は見せない。任意の参加とし、記録はP01等の識別子で残す。録画を前提にせず、発言と操作のメモで実施できる。

冒頭の説明例：

> この画面が初めての人にも使いやすいかを確認します。あなたの知識や能力の試験ではありません。考えていること、迷ったことをできる範囲で話してください。画面の説明は自由に読めます。分からない場合は、そのまま伝えてください。

事前に計算の結論、検出力との違い、押すボタンを説明しない。各課題の最初の回答を記録してから中立的に「そう考えた理由は何ですか」「どの表示を見ましたか」と尋ねる。困った時は、まず「今、何をしようとしていますか」と確認する。助けを求めた場合や進めなくなった場合は支援してよいが、支援前後を区別する。2分程度進展がなければ続行希望を確認し、未完了として次へ移れるようにする。この時間を合否基準にはしない。

## 参加者に提示する5つの課題

一度に1課題ずつ提示する。課題1・3では、操作直後の自由説明を先に記録する。

1. **最初の比較**：「画面の二条件の例を使います。125人が参加し、各人が各条件で17語に取り組む計画です。ばらつきについては最初の値を使ってください。人数か単語数のどちらか一方を25%増やす場合を比較してください。表示から何が分かると思いますか。」
2. **中断と再開**：「このツールの概要画面を一度見てから、いま作った比較へ戻ってください。戻る前後で内容が同じか確認してください。」
3. **別の仮定との比較**：「いまのばらつきの仮定を残したうえで、単語ごとの効果のばらつきを0.60とする別案も残し、比較してください。他の入力は同じにします。何が変わりましたか。計画を選ぶ際に、どう扱いますか。」
4. **入力の修正**：「人数の欄に125.5と入力すると何が起きますか。125人に直して、比較できる状態に戻してください。」
5. **保存と引継ぎ**：「いまの比較を後からRで再現できる形で保存してください。保存したものに何が含まれ、それを実行すると何が得られると思いますか。」

Rを普段使う参加者のみ、任意の追加課題として空の作業フォルダで出力Rを実行し、CSV・PDFを見つけてもらう。R未経験者が実行できないことをWeb操作の失敗として採点しない。ダウンロード操作、ファイル発見、R実行は別々に記録する。

最後に、課題1・3の自発的な説明とは別の確認として以下を尋ねる。結論だけでなく理由も記録する。

- 「この画面だけで、効果を検出できる確率が80%以上だと言えるでしょうか。」
- 「最初に入っていた人数やばらつきの値を、そのまま自分の研究の推奨設定として使えるでしょうか。」
- 「2つの仮定で同じ結論になったら、他の仮定でも必ず同じと言えるでしょうか。」

これは誤解を明示的に尋ねる補助質問なので、正答しても自発的に理解できた証拠には置き換えない。質問後に必要な説明を行う。

## 観察者用の期待結果・判定基準

| 課題 | 操作の達成 | 解釈の確認 |
| --- | --- | --- |
| 1 | N=125、条件当たり17語、増加25%。実際の比較人数は157人、単語を増やす案は総44語 | 初期仮定では人数追加のSD減少6.1%、単語追加4.9%。新しい学習者・単語を抽出して研究を繰り返す際の平均的な条件差のばらつき、と説明できる。検出率や平均効果の増加とは解釈しない |
| 2 | 再開後も人数・単語数・増加率が同じ。例の再読込を再開と混同しない | ページ内の再開と、ブラウザの再読み込みによるリセットを区別できるか |
| 3 | 単語側SDが0.18と0.60の2セット。他の仮定・共通人数・増加率は同じ | 今回は人数追加優位から単語追加優位へ変わる。結論が仮定に依存することを述べ、都合のよい結果だけを採用するのではなく仮定の根拠を検討する。SDは単語難易度そのもののばらつきではない |
| 4 | 小数人数で比較・出力が停止し、125へ修正すると回復。保持セットも残る | 無効表示のまま以前の結果を有効と扱わず、直す項目を識別できる |
| 5 | `.R`ファイルを保存して見つける。保持セットを含む現在の比較が対象 | 仮定・計算・比較CSV・曲線CSV・PDFと、保持セットの比較CSVを再現するコード。回答データのシミュレーション、モデル当てはめ、検出力計算ではない |

専門用語を正確に暗唱する必要はない。課題1で細かい数値を覚えていないことと、結果の意味を誤解していることを区別する。明示的な補助質問はいずれも、この画面だけでは根拠にならないと理由付きで答えることが期待される。

操作は「自力完了／支援後完了／未完了」、理解は「意味を説明／部分的・不明／明確な誤解」と記録する。説明を引用し、観察者が不足部分を好意的に補わない。合計点で操作の成功と誤解を相殺しない。

優先修正とする例は、比較や保存まで進めない、再開で状態が変わったと気づかない、検出力・推奨人数として出力を使おうとする、仮定変更の結論逆転を一般的な推奨と受け取る、といった問題。発生人数だけで順位を決めず、研究上の判断への影響と回復可能性も記録する。少人数全員が完了しても「初心者全般に使いやすい」とは結論しない。

## 利用者の指摘を受けた修正：スライダー操作中のスクロール

同日、スライダーを動かすとページ上部へ戻るとの指摘を受けた。Chromeで、スライダーにTabで移動し、右矢印で100%から105%へ変更すると上部のヘッダーまで戻ることを再現した。前の操作検証では数値・フォーカスを確認したが、スクロール位置の測定が不足していた。

原因は、正常な更新でも`clearEffectResults()`が比較画面全体を非表示にし、その状態でSVGの`clientWidth`を読んでレイアウト計算を発生させていたこと。ページが一時的に短くなり、スクロール位置が戻っていた。正常な再計算は既存の表示を保ったまま更新し、結果を消す処理は不正入力・設計ブロック時に限定した。グラフ幅も比較領域を表示した状態で測るようにした。

修正版を読み込んだChromeでの計測：

| 操作 | 計測結果 |
| --- | --- |
| 通常幅で右端側から12回連続の左矢印操作（140%→85%） | `scrollY=723`、スライダー上端`427.90px`を全回で維持。フォーカスもスライダーに残る |
| マウスで85%→200%へドラッグ | 同じスクロール位置・スライダー位置を維持 |
| マウスで200%→0%へドラッグ | `scrollY=723`を維持。0%の説明が短くなるためスライダー上端は`404.59px`へ変化したが、ページ上部への移動は起きない |
| 390px幅で8回の右矢印操作（10%→45%） | `scrollY=1049`、スライダー上端`520.16px`を全回で維持。フォーカスも維持 |

`test.mjs`に、一回の更新内でも比較領域を非表示→再表示しないことをMutationObserverで検出する回帰テストを追加した。実ブラウザの位置計測とは別に、JSDOMでも原因となる更新を検出できる。静的Webのビルド・テスト・匿名化ゲートと、2,000ステップを含むストレステストは成功。不正入力時の結果消去、保持セット、R出力の検証も通過した。

## 追加修正：説明の長さによる位置ずれと操作の継続（2026-09-20）

上記の0%切り替え時に残っていた約23pxの位置ずれも修正した。値によって長さが変わる結論・説明をグラフとスライダーより下へ移し、グラフ→スライダー→選択値→説明の順にした。固定の空白やスクロール位置の強制復元は追加していない。

仮定セットの **Use in chart** は、適用後にスライダーをフォーカスする。セット削除後は次のセットの削除ボタン、次がなければ前のセット、すべて削除した場合は仮定変更ボタンへフォーカスを移す。比較領域の冒頭に戻らず、その場で操作を続けられる。

更新したHTMLと以前のJavaScriptがブラウザキャッシュで混在する例も観察した。ビルド時に既存SHA-256からCSS・スクリプトURLのクエリを更新し、新しいHTMLが対応するアセットを要求するようにした。通常の再読み込み後、新しい0%説明文が読み込まれたことをChromeで確認した。

修正後のChrome計測（先行するフォーカス移動・スクロールが終了してから測定）：

| 操作 | 結果 |
| --- | --- |
| 通常幅で0%→200%→0%→200%→0%→5% | 全回で`scrollY=388`、スライダー上端`455.77px`、フォーカスを維持 |
| 390px幅で0%→200%→0%→200%→0%→5%→10%→5% | 全回で`scrollY=610`、スライダー上端`401.34px`、フォーカスを維持。ページ幅も390px |
| 390px幅でSet 1をグラフに適用し、右矢印で5%→10% | 適用後はスライダーをフォーカス。続く矢印操作でも`scrollY=610`、上端`401.34px`を維持 |
| 3セットから順次削除 | 残る削除ボタンにフォーカスを維持し、最後の削除後は仮定変更ボタンへ移動 |

`test.mjs`には説明がスライダーより後にあること、適用・削除後の具体的なフォーカス先、HTMLのアセットURLとビルドハッシュの一致を追加した。`npm --prefix apps/design_planner_web run check`成功。`npm --prefix apps/design_planner_web run test:stress`も成功し、15,000数値条件、2,000混合操作、R一致104条件、極端な入力のR出力3例を通過した（5.30秒、DOM要素数は初期・最大とも694）。同じソースで再ビルドし、HTMLとメタデータのバイト一致も確認した。

これは操作・実装の検証であり、初心者参加者による理解度評価ではない。今回の追加検証はキーボード操作を中心とし、全ブラウザ、実機タッチ操作、スクリーンリーダーの音声出力を網羅していない。計算式の変更と公開デプロイは行っていない。

## 公開後の修正：Evaluate structureの結果を見つけられない（2026-09-20）

ユーザーの指摘を公開版で再現した。クリック時の計算は実行されていたが、
結果見出しは画面上端より529px上にあり、フォーカスはボタンに残っていた。
入力変更時にも自動評価されるため、同じ入力でボタンを押しても変化を認識
できなかった。直前の公開確認では、この明示的な評価操作の結果への導線を
検証できていなかった。

明示的なクリックでは保留中の自動評価を取り消して最新の入力を評価し、
結果見出しをフォーカスして表示する。入力に伴う自動更新では移動しない。
ボタン付近の説明も、自動評価と結果へ移動する操作の違いを明記した。

回帰テストは修正前に結果へのフォーカス検査で失敗し、修正後に成功した。
通常・ブロック時の結果表示と、自動評価時に入力フォーカスを維持することを
確認する。静的Webのビルド・DOM・匿名化チェック、2,000混合操作を含む
ストレステストも成功。Chromeのローカル版では、ガイド・詳細ツール両経路で
結果をフォーカスし、通常幅・390px幅で見出し上端が約20pxとなった。
