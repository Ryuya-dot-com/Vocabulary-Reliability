# Static Claim Router and Design Audit

This is the always-available, R-independent frontend for the vocabulary
reliability design planner. The default entry is a guided learners-or-words
comparison. **All research tools** opens the manuscript's four inferential
targets, aligned evidence, minimum reporting, claim boundaries, and design audit. It is an asset-only Cloudflare Workers project: no
Worker script, database, user-data upload, session state, or R request is on
the critical path.

The browser uses the same `design_audit.js` contract tested against the R
implementation in `../design_planner/design_audit.R`. `build.mjs` copies the
versioned schema, shared adversarial fixtures, and validation registry into the
deployable `public/` directory and writes SHA-256 metadata. The four branches
are generated from `data/inferential_target_registry.json`, whose content is
aligned with main-text Figure 1 and Supplement S2.2.

The build also adds content-hash query strings to the page's CSS and script
URLs, so updated HTML requests matching assets instead of reusing older cached
code. Rebuilding unchanged sources produces identical HTML and metadata.

Two calculations remain available without an R session. `claim_math.js`
implements the same expected-alpha identity and participant/item
effect-generalizability projection as the pure R functions in
`planner_functions.R`. Shared JSON fixtures test the two runtimes at a fixed
`1e-12` tolerance. These are typed-assumption sensitivity projections, not
observed estimates, power results, or validation certificates. The effect
projection is enabled only for an exact two-condition, counterbalanced
participant × item design with both condition slopes and no additional
generalization slope.

Branch 2 also exposes the two bundled simulation families as an exact-only
reference browser. `reference_grids.json` is generated and verified by R from
the three provenance-checked CSV snapshots. It contains 70 published rows and
never interpolates, extrapolates, or applies a row automatically to the current
design. A structurally blocked design may inspect a row, but the row cannot
clear the design gate or be relabeled as transferable power.

`decision_rules.json` is also generated by R. It assigns every current or
planned calculation to one of three execution pathways: `browser_static`,
`short_r_api`, or `offline_async`. The synchronous R pathway is explicitly
unimplemented and no public feature depends on it. Monte Carlo simulation and
model fitting are prohibited in browser/page requests. R-generated
`golden_test_fixtures.json` is bundled beside the rules so the DOM test can
compare JavaScript decisions with the R outputs used to build the artifact.

The validation registry is intentionally empty. A structurally estimable design
therefore remains `Estimable but fragile` until a complete parameter envelope
has passed the required simulation review. A user-entered `validation_id`
cannot promote a design on its own.

## Score definitions and model specification

Two optional disclosures extend the guided example without adding required setup:

- **Define target scores and known-word fillers** compares a single learner's
  fixed-target, initially-unknown-target, and whole-test scores. It records the
  overlap of pretest-known and posttest-correct target responses; zero eligible
  targets is undefined, not zero. Fillers never inflate the projection's word
  count. Counts here are an independent illustration, not empirical reliability
  estimates or evidence of motivation benefits. Unknown-only scoring disables
  the balanced fixed-target projection and the common-item alpha identity. Both the JSON and R exports retain the
  primary scoring policy. The score download reproduces the arithmetic in base R.
- **Add fixed predictors and their random slopes**, inside the structural audit,
  accepts numeric/categorical predictors, categorical level counts, condition
  interactions, within-facet variation declarations and requested slope facets.
  Requested interaction slopes require both declared variations. Added slopes
  inherit diag/us structure; with no condition slope they use diag. A predictor
  slope does not require a condition slope. The nominal fixed coefficient count
  includes the intercept and is not a full-rank guarantee. A facet's Fixed role
  remains fixed context, not an estimated covariate adjustment.

Extra predictors disable the existing SD curve, rather than silently reusing
its simpler formula. The structural result is explicitly for the base condition
structure. The separate model specification validates names and slope declarations,
not data support or statistical performance. Resetting a design example clears
added predictors; restarting the guided example also resets the scoring example.

**Download analysis specification in R** provides the current formula and
`fit_study(data)`. It runs the scoring illustration but does not fit automatically.
The function requires binary response data, explicit target/filler item roles,
matching predictor/grouping columns, and lme4 supporting the displayed covariance
syntax (tested with 2.0.6). It excludes fillers, applies the chosen pretest-known
policy, checks missing data and fixed-effect rank, and reports singular fits.
This is an analysis template, not a Monte Carlo power simulator. Interactions
among added predictors, arbitrary formulas, and covariance-parameter planning
are not provided by this editor. Any precision/power study still needs an explicit
data-generating model and design-specific simulation.

Run `node test.mjs --check-r` to check score parity and actual numeric/categorical
GLMM fits, including target/filler and pretest-known filtering. Ordinary `npm test`
covers invalid counts, empty eligibility, invalid slope declarations, duplicate
and unsafe names, numerical gating, downloads and example reset.

## Learners-or-words planning workflow

Choose **Explore the two-condition example** to load a counterbalanced
participant × item structure. The initial 120 learners and 30 total words are
illustrative values, not a recommended design. The comparison's counts remain
separate from the structural audit's recorded counts.

The interface shows one stage at a time:

1. **Set up:** enter two counts. Variation assumptions are editable in a
   disclosure, with their current values summarized outside it. Each variation
   input has a concrete example. A further guide explains how to use comparable
   estimates or explore plausible alternatives without treating defaults as
   recommended values.
2. **Compare:** an interactive SVG shows learner and word expansions
   from +0% to +200%, sampled every 5%. Hover previews a point; click or the
   keyboard-accessible range control selects it. Actual counts round upward.
   Selected numeric readouts and a plain-language takeaway follow the slider,
   so changing the explanation's length cannot move the controls above it.
   The takeaway states which selected expansion reduces variation more, with
   actual study sizes and SD reductions. Ties, zero increase and zero included
   variation have separate explanations. **Try different assumptions** returns
   to the open inputs without resetting the comparison.
   The readouts, interpretation, exact table and audit JSON all use the selected
   increase. The graph resizes without shrinking its labels to unreadable sizes.
   **Keep these assumptions** retains up to three distinct sets of learner/word
   slope SDs, memory variation and adjustment status. The comparison opens after
   keeping a set and displays side-by-side cards (stacked on narrow screens).
   Counts and the selected increase are shared: changing them recalculates every
   kept set. The summary distinguishes agreement, reversals, ties and undefined
   reductions. **Use in chart** restores a set's assumptions without replacing
   the common counts and focuses the slider for continued exploration. Removing
   a set focuses the next set's remove button, the previous set if none follows,
   or the change-assumptions button when none remain. Sets stay in memory until
   page reload.
3. **Save & reproduce:** download a standalone base-R script with all inputs,
   the selected comparison and the full 41-point curves. Running it writes
   comparison/curve CSVs and a PDF in the working directory. The script is
   previewable before download. A reporting draft records the assumptions.
   When sets are kept, the script also writes
   `vocabulary-assumption-comparison.csv`, including their inputs, shared counts,
   projected SDs, reductions and comparison direction. The PDF remains the
   current chart's two curves. The audit JSON includes the same kept-set results.

After the first start, **Overview → Resume your comparison** returns to the
current stage with the inputs, design, selected increase and kept sets preserved.
**Restart with example inputs** explicitly reloads the example structure,
counts, variation and 100% increase; kept sets remain and use the reset common
counts. Reloading the page still clears all page state.

Keyboard users can use the skip link, native disclosure controls and range
slider. The slider exposes a stable label plus its percentage and actual rounded
counts to assistive technology. Guided headings use the appropriate levels for
the simplified page; field errors are linked to the affected input alongside
its existing help, and focus outlines include scrollable comparison regions.
Valid slider updates keep the comparison in the document layout so chart
measurement cannot collapse the page and send the user back to the top.

The chart uses native SVG and form controls, with solid/dashed curves and an
exact-value table; it does not load Plotly or another runtime dependency.
Script downloads use a local Blob. No network or R server is involved.

Memory adjustment changes both projected SD and the bottleneck classification.
Invalid inputs or blocked designs clear results and R code, disable export and
forward navigation, and return the user to setup. Other research tools and the
structural audit remain accessible separately.

Very small nonzero SDs use scientific notation rather than rounding to zero.
Calculations reject overflowing or subnormal positive variance groups, including
failures in a kept set, and browser inputs distinguish a true zero from a
nonzero string that underflows during conversion. Starting counts are capped at
`floor(Number.MAX_SAFE_INTEGER / 300)` so every expanded count on the curve can
be rounded reliably. These are numerical limits, not scientifically validated
parameter ranges.

This is variation of the average latent effect across sampled learners and
words, not GLMM estimation SE or power. Equal proportional increases do not
imply equal costs, and adding words may change exposure, fatigue, or task
difficulty. Users should vary plausible slope SDs before choosing a design.
Agreement across the kept sets only concerns those selected assumptions and
study sizes; it is not a validation or robustness guarantee for other values.
The export reproduces the closed-form projection; it is not a response
simulation or a fitted analysis. No validated envelopes are introduced.

The layout uses clear section hierarchy, restrained color, and disclosures,
informed by the supplied [UI Library](https://design-library.jp/ui/) reference.
A novice usability study has not yet been conducted. The five-task protocol,
separate operation/comprehension criteria, observer record and completed
keyboard/DOM checks are in `../../review/web_planner_usability_20260919.md`.
Actual screen-reader speech testing remains pending.

## Build and test

The recommended repository-level runner captures successful command output and
prints one summary line. If a command fails, it expands that command's exit
status, stdout, and stderr. Run the quick cross-runtime/static suite from this
directory with:

```sh
npm run --silent check:quick
```

Include the slower Shiny planner suite with:

```sh
npm run --silent check:all
```

Use `node ../../scripts/run_design_planner_checks.mjs --verbose` when successful
command output is needed for investigation. The lower-level static-only command
remains:

```sh
npm install
npm run check
```

The static test suite checks the staged navigation, chart selection, invalid-input
recovery and download content, plus takeaway changes, ties, rounded comparisons,
kept-set isolation, duplicate/capacity limits, removal, reuse and returning to
assumptions with inputs preserved. To additionally execute eight exported R
examples (including unadjusted/adjusted assumptions, rounded counts, zero
variance, kept-set comparisons and no increase), with CSV parity checks for
all curve points and kept-set results, plus PDF generation:

```sh
npm test -- --check-r
```

This optional check requires Rscript; the default static build/test does not.
An illustrative export is in
`../../outputs/design_planner_examples/vocabulary-design-sensitivity.R`.

Run the deterministic engineering stress suite (also requires Rscript) with:

```sh
npm run test:stress
```

It checks 12,000 randomized projection cases against an independent `hypot`
calculation, 3,000 alpha cases, 14 invalid-input probes and 2,000 mixed JSDOM
operation steps. It also compares 104 cases with the Shiny R function and runs
three generated R exports with extreme numerical inputs. The fixed seed is
printed with the results. Mixed operations cover retained assumptions,
navigation, invalid-input recovery, design blocking, hover and mocked downloads;
they do not save files into the user's Downloads folder. DOM size and download
URL cleanup are checked, but this is not a browser heap/leak audit, concurrent
hosting load test or statistical validation of the assumed study. See
`../../review/web_planner_stress_20260919.md` for findings and limits.

## Deployment validation

### Cloudflare Pages publication

The publication route selected on 2026-09-20 is Cloudflare Pages Direct Upload.
Pages uses a project-based `<project-name>.pages.dev` hostname, avoiding the
identifying account-wide `workers.dev` subdomain. Use a generic project name;
this does not guarantee anonymity if the same code is publicly attributable
elsewhere. Do not add author-account or repository links to the served app.

From the repository root, after the checks below pass:

```sh
npm --prefix apps/design_planner_web run check
# Create the project once, using a non-identifying name:
apps/design_planner_web/node_modules/.bin/wrangler pages project create <project-name> --production-branch main
apps/design_planner_web/node_modules/.bin/wrangler pages deploy apps/design_planner_web/public --project-name <project-name> --branch main
```

Only `public/` is uploaded; `_headers` applies the app's CSP and indexing/referrer
policy. After deployment, verify the HTTPS responses and served asset hashes
against `public/build-meta.json`. Pages may also create deployment-specific
URLs; these differ from Workers' `preview_urls` setting. The existing Workers
configuration and dry-run script remain available as an alternative, subject
to the Workers hostname checks below. Neither a Pages deployment nor a GitHub
push updates the manuscript or OSF package.

### Content checks and alternative Workers publication

The normal check includes an anonymous-release gate. It allows only the 16
expected static assets and fails if a deployable file contains an author name,
institution, email address, ORCID-like identifier, grant identifier, local
home/Dropbox path, or author metadata. It also requires versioned Preview URLs
to be disabled:

```sh
npm run check
```

Before publishing, verify the proposed account-wide `workers.dev` subdomain as
well. Use a generic, dedicated subdomain that is not shared with identifying
personal or institutional Workers:

```sh
npm run check:anonymity -- --account-subdomain methods-review-a7f3
```

Check Wrangler authentication without printing the login email, account name,
or account ID:

```sh
npm run check:cloudflare-account
```

Wrangler's `whoami` output does not always expose the account-wide
`workers.dev` subdomain. When the preflight reports
`manual_dashboard_check_required`, read it under **Workers & Pages → Your
subdomain** and pass that exact public label back to the preflight:

```sh
npm run check:cloudflare-account -- --verified-subdomain <dashboard-subdomain>
```

The command treats private account metadata, such as the display name or login
email, as informational only and does not print its value. Those fields are not
part of a public `workers.dev` URL. A result of
`CLOUDFLARE_RELEASE_ACCOUNT_READY=no` means that the public subdomain is still
unknown, invalid, or identifying; do not deploy until that public-hostname gate
passes.

Optionally use a directory-bound Wrangler authentication profile so a later
deploy cannot silently target a different Cloudflare account. While signed into
the intended release account, run:

```sh
npx wrangler auth create review-release
npx wrangler auth activate review-release .
npm run check:cloudflare-account
```

The local `.wrangler/`, `.env*`, and `.dev.vars*` paths are ignored by Git. Do
not commit an account ID, OAuth token, API token, or login email. The dashboard
must show a generic public `workers.dev` subdomain before the production deploy
command is used. The same account is acceptable if that public subdomain is
anonymous and is not already linkable to identifying personal or institutional
Workers; a separate release account is optional defense in depth.

With the current Worker name, that example would produce
`https://reliability-design.methods-review-a7f3.workers.dev`.
The account subdomain must be selected separately in the Cloudflare dashboard;
it is not stored in this repository.

The `deploy` script performs a Wrangler dry run and does not publish anything:

```sh
npm run deploy
```

Actual publication should be a separate, deliberate `wrangler deploy` step
after the review and anonymity checks are complete. For double-anonymous
review, use an account subdomain with no public link to the author, keep
`preview_urls` disabled, and do not add a custom domain registered or already
used under an identifying name. A dedicated release account can further reduce
cross-project linkability but is not required merely because its private
metadata is identifying. The review build also sends
`X-Robots-Tag: noindex, nofollow, noarchive` and `Referrer-Policy: no-referrer`;
these reduce accidental discovery and referrer leakage but do not make a public
URL confidential.

The configuration follows Cloudflare's current Workers Static Assets guidance:
<https://developers.cloudflare.com/workers/static-assets/>.
